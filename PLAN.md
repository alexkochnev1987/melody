## 1. Подтверждённые решения

- **Аудио:** YouTube воспроизводится на **телефоне ведущего**, звук выводится на **Bluetooth-колонку**. Телевизор показывает только публичный игровой экран.
- **AI-поиск:** три сценария — поиск по описанию пользователя, самостоятельное исследование музыкальных подборок по критериям и ручной поиск/редактирование. AI предлагает кандидатов; YouTube API находит конкретные видео.
- **Подсказки:** смешные подсказки на основе проверенного текста песни или достоверного описания смысла; допустим резервный вариант на основе известных модели сведений, но с маркировкой низкой уверенности и обязательной проверкой. Сохранять источник/метод формирования.
- **Правила:** настраиваемые очки, штрафы, подсказки, время ответа, число раундов и другие параметры.
- **Хранение:** постоянные плейлисты, история завершённых игр, очки игроков и статистика.
- **Разработка:** начать **локально** в указанной папке, GitHub + CI, деплой Next.js на **Vercel с первого этапа**; управляемая БД из экосистемы Vercel/Marketplace; AI через серверный API-ключ.

## 2. Цель и MVP

Домашняя музыкальная игра для ориентировочно 5–30 участников. Игрок открывает ссылку/QR на телефоне, вводит имя и нажимает STOP, чтобы первым ответить. Ведущий контролирует YouTube-плеер и оценивает устный ответ. Телевизор отображает состояние игры и рейтинг без спойлеров. Организатор заранее собирает и редактирует плейлисты, в том числе с помощью AI.

**Критерий MVP:** провести 20–30 раундов с 10+ телефонами, не потерять результаты после перезагрузки и переподключения, не раскрыть ответы до команды ведущего.

## 4. Архитектура

```text
Next.js (TypeScript, App Router) на Vercel
├── UI: Host / Display / Player / Playlist Builder / History
├── HTTP API: песни, плейлисты, AI, история, настройки
├── Realtime transport: WebSocket, если выбранный Vercel runtime поддерживает нужный сценарий
├── Domain: game state machine, scoring, buzzer arbitration
├── Integrations: YouTube Data API, YouTube IFrame API, AI provider
├── PostgreSQL: постоянные данные
└── Redis (managed, при необходимости): атомарный STOP, временное состояние, pub/sub
```

**Важное архитектурное условие:** до выбора транспорта провести spike на актуальном Vercel runtime. WebSocket/Next.js интеграция и лимиты выполнения могут изменяться. Не хранить состояние комнаты в памяти Function. Если нативный WebSocket на Vercel окажется нестабильным, заменить только транспорт на managed realtime (например, Ably/Pusher) либо отдельный небольшой WebSocket-сервис; доменная логика и UI остаются прежними. **Vercel сам по себе не является базой данных:** PostgreSQL подключается как отдельный managed provider через Vercel Marketplace/интеграцию.

## 5. Состояния игры и правила

```text
LOBBY → READY → PLAYING → BUZZED → JUDGING
                            ├── correct → REVEALED → NEXT/FINISHED
                            └── incorrect → PLAYING или REVEALED
```

- Сервер — единственный источник истины для статусов, очков, доступности STOP и прав игрока.
- Победитель STOP — **первое валидное событие, принятое сервером**; физически первый тап при разной задержке сети гарантировать невозможно.
- Атомарный claim (`roomId`, `roundId`) с TTL/версией; повторные команды идемпотентны по `commandId`.
- Ведущий может вручную поставить паузу, продолжить, пропустить, раскрыть ответ, изменить баллы и отменить последнее решение.
- После ошибки игрок может быть заблокирован до следующего раунда (настройка).
- Подсказки 1/2/3 уменьшают максимально доступные очки согласно правилам.
- После reconnect клиент получает **полный snapshot** с `revision`, а не полагается на пропущенные события.
- Музыка играет только на устройстве ведущего; команда `round:buzzed` ставит YouTube-плеер на паузу. Если браузер блокирует возобновление, показать ведущему ручную кнопку.

### Предлагаемые realtime-события

| Направление | Событие | Содержание |
|---|---|---|
| Player → server | `player:join` | roomCode, sessionToken, displayName |
| Player → server | `player:buzz` | roundId, commandId |
| Host → server | `host:startRound` | roundId, commandId |
| Host → server | `host:judge` | roundId, playerId, correct, commandId |
| Host → server | `host:hint` | roundId, hintLevel, commandId |
| Host → server | `host:skip` / `host:reveal` | roundId, commandId |
| Server → room | `game:snapshot` | role-filtered state, revision |
| Server → room | `round:buzzed` | winnerId, roundId, revision |
| Server → room | `score:updated` | scores, revision |
| Server → room | `round:revealed` | public answer, revision |

Авторизовать **каждую** host-команду, не доверять переданному клиентом `playerId` и не отдавать секреты через общую рассылку.

## 6. Модель данных

- `User/Organizer`: владелец плейлистов, вход организатора (простая защищённая авторизация).
- `Song`: title, artist, youtubeVideoId, duration, clipStartSeconds, clipEndSeconds?, language, tags, difficulty, verificationStatus.
- `SongSource`: provider, sourceUrl, sourceType (`lyrics` / `meaning` / `model_knowledge`), confidence, checkedAt, licenseNotes.
- `Hint`: songId, level (1–3), text, sourceId?, reviewedAt, generatedByModel.
- `Playlist`: ownerId, title, description, filters, createdAt, updatedAt.
- `PlaylistSong`: playlistId, songId, position, overrides.
- `Game`: roomCode, playlistId, hostId, rulesSnapshot, status, startedAt, endedAt.
- `GamePlayer`: gameId, stablePlayerId, displayName, score, joinedAt, lastSeenAt.
- `Round`: gameId, songId, position, status, startedAt, revealedAt.
- `Buzz/Answer`: roundId, playerId, serverReceivedAt, outcome, awardedPoints, commandId.
- `ScoreEvent`: gameId, roundId, playerId, delta, reason, commandId, createdAt.
- `GameStats`: вычисляемая статистика или materialized aggregate: победы, точность, количество ответов, средние очки, история игр.

Хранить **события начисления** (`ScoreEvent`) для аудита и отмены. `score` — производное/кэшируемое значение; итоговые результаты сохранять в PostgreSQL. При изменении правил сохранять snapshot в игре, чтобы история не менялась задним числом.

## 7. AI Song Discovery и YouTube Search

### Режимы поиска

1. **Prompt-to-playlist:** «30 русских и зарубежных хитов 2000–2015 для вечеринки, средняя сложность» → AI предлагает структурированный список исполнителей и песен.
2. **AI research:** AI исследует доступные надёжные источники/подборки через явно разрешённый поисковый инструмент; записывает ссылки на источники, исключает дубликаты и предлагает кандидатов. Не считать ответ модели без источника фактом.
3. **Manual:** ручной ввод исполнителя/названия, YouTube-поиск и добавление по URL.

### Pipeline

```text
User prompt / filters
  → AI discovery (structured JSON + sources + confidence)
  → dedupe & normalization
  → YouTube Data API search (server-side, throttled, cached)
  → candidate ranking (official / original / embeddable / region / duration)
  → organizer preview & confirmation
  → meaning / lyrics source resolution
  → AI funny hint generation (3 levels)
  → spoiler / accuracy validation
  → manual review
  → published playlist
```

**Поиск YouTube:** не использовать YouTube как источник полного текста песни. Проверять `videoEmbeddable`, длительность, региональные ограничения и фактическое воспроизведение. Квоты и стоимость `search.list` сверить с текущей консолью Google Cloud перед внедрением, ограничить количество поисков, кэшировать `query → candidates`, иметь retry/backoff.

**AI-поиск:** модель не должна выдумывать найденные видео, ссылки или источники. Сначала возвращает `artist/title` и обоснование; конкретный `videoId` приходит только из YouTube API. Результаты AI всегда черновики до проверки.

**Подсказки:** генерация по разрешённому тексту или проверенному пересказу смысла; если нет источника — явно обозначить `model_knowledge` и `needsReview`. Не хранить и не показывать полные тексты песен без прав. Проверять отсутствие названия/исполнителя/узнаваемых строк, давать регенерацию одной подсказки и ручное редактирование. Уровни: загадочная / средняя / почти очевидная.

**API-ключи:** `OPENAI_API_KEY` (или иной выбранный AI-провайдер), `YOUTUBE_API_KEY` — исключительно серверные env vars. Лимиты запросов, бюджеты, логирование ошибок без раскрытия секретов. Внешний AI — ненадёжная зависимость: таймауты, retries, schema validation, moderation и возможность продолжить вручную.

## 8. YouTube и устройства: обязательный spike

**Конфигурация:** телефон ведущего с видимым встроенным YouTube-плеером (соблюдать правила YouTube), Bluetooth-колонка, телевизор с отдельным `/display`.

Проверить на реальном iPhone (Safari/PWA) и Android (Chrome):

- запуск первой песни по жесту пользователя;
- переход к следующей песне и `seekTo(startSeconds)`;
- STOP с другого устройства → пауза;
- продолжение после неверного ответа; запасная кнопка при блокировке autoplay;
- стабильность Bluetooth, задержка звука, блокировка экрана/сворачивание приложения;
- работа при нестабильном Wi-Fi;
- доступность конкретных YouTube-видео и региональные ограничения;
- ТВ-дашборд отдельно от плеера, без показа ответов.

**Не делать:** скрытый/микроскопический YouTube-плеер, извлечение аудиодорожки, скачивание музыки, обход ограничений встраивания. Если телефон не позволяет надёжно воспроизводить последовательные треки, запасной сценарий — ноутбук ведущего с тем же host UI и Bluetooth-колонкой.

## 9. Безопасность

- Секретный host-token, отдельные player-session tokens; roomCode не является административным ключом.
- Проверка ролей на сервере, rate limiting, ограничение размера имени и пользовательских prompt.
- Защита от повторных `buzz`/`judge`, идемпотентность команд, аудит начислений.
- Не отправлять ответы, скрытые видео-ID и приватные подсказки игрокам до раскрытия.
- Серверная валидация Zod, безопасное хранение секретов, no secrets in browser bundle.
- Политика хранения и удаления истории, минимизация персональных данных.

## 12. Открытые решения перед кодом

1. **AI-провайдер:** OpenAI API по умолчанию; подтвердить модель и бюджет.
2. **Провайдер PostgreSQL:** выбрать доступный через Vercel Marketplace (например, Neon) и тариф; это отдельная управляемая БД, не встроенная БД Vercel.
3. **Redis/realtime:** выбрать провайдера после spike; не вводить Redis без измеренной необходимости, но предусмотреть атомарный механизм для STOP.
4. **Авторизация организатора:** пароль/магическая ссылка/OAuth; для MVP можно простой защищённый вход.
5. **Правила по умолчанию:** +10 правильный, −5 неправильный, подсказки снижают награду до 7/5, ошибившийся игрок не может повторно нажать в текущем раунде — всё настраивается.
6. **Статистика игроков между играми:** объединение по постоянному профилю или только по сессии/имени. Одинаковые имена не означают одного человека.
7. **Источники для AI research и текстов:** согласовать допустимые сервисы и права на использование; без подтверждения источника AI-вывод маркировать как требующий проверки.

## 13. Что НЕ входит в первый релиз

- Распознавание ответов по микрофону и автоматическая оценка.

- Масштабирование на сотни одновременных комнат до подтверждения спроса.
